# AGENTS.md

FastAPI + SQLAlchemy (MySQL) expense-tracking API + Next.js + TypeScript frontend. Python 3.11, deps in `backend/requirements.txt`; Node.js deps in `frontend-next/package.json` (Next 15, App Router, React 19 — the old Vite SPA `frontend/` was removed).

## Change rules

- Limit every change to the scope of the requirement at hand. Do not refactor or "improve" unrelated code.
- Do not alter the architecture of the repository/application/system (structure, entrypoints, wiring, dependencies, config, Docker setup).
- Do not alter the database and/or data persistence models (`backend/src/models/*`) unless the user explicitly requests it — the only sanctioned exception so far is the `Account.bank` column (added on request).
- NEVER run tests/checks nor build/start/stop Docker containers — the user does all of that manually. Only prepare the changes and hand over the exact commands for them to run.
- Always use object-oriented programming (OOP) in any code written or changed.
- When implementing new functionality or refactoring existing code, add docstring-style comments (docstrings); do not add comments that add no value or meaning.
- After implementing a change, review the resulting diff for duplicated logic, redundancies and dead code, and consolidate them before considering the task done.
- Whenever changes are applied, update `AGENTS.md` accordingly.

## Run

- Setup: `python -m venv myenv` + `myenv\Scripts\activate` (Windows) + `pip install -r requirements.txt`. The `myenv` venv is gitignored.
- App (local): `uvicorn main:app --reload` — **must run from repo root** (inside `backend/`). Imports are mixed absolute (`backend.src.models`, `backend.src.db.config`) and relative (`..db.config`, `.security`), so a `src`-relative cwd will break imports.
- Docker: `docker compose up --build` runs a single `fastapi` container. SQLite DB (`DB_URL=sqlite:////app/data/expense_app.db`) persists via a **bind mount of the repo root** (`./:/app/data`), not a named volume, so the container writes the canonical dev DB at repo-root `expense_app.db`. Dev mode (`./backend:/app` + `APP_RELOAD=true` → `--reload`) comes from `docker-compose.override.yaml`, applied automatically; run prod-only with `docker compose -f docker-compose.yaml up --build`. `backend/scripts/entrypoint.py` seeds default categories, then launches uvicorn. (The old `backend/data/` bind mount is gone; `backend/data/` is no longer used.)

## DB config

`backend/src/db/config.py` differentiates environments through `APP_ENV` (`dev` default, `prod`). The connection URL is resolved with priority `DB_URL` → `DATABASE_URL` (Render's standard name); in `dev` a missing URL falls back to the legacy `DB_*` MySQL build (`DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`). In `prod` a missing URL **and** a SQLite URL are hard errors (fail-fast, so production never runs on an ephemeral SQLite file) — `prod` uses the Render PostgreSQL **internal** connection string. PostgreSQL URLs are normalized to the `psycopg2` driver (`postgres://`/`postgresql://` → `postgresql+psycopg2://`). SQLite engines get `connect_args={"check_same_thread": False}`; PostgreSQL engines get `pool_pre_ping=True` + `pool_recycle=300` (Render's free DB drops idle connections) and accept an optional `DB_SSL_MODE` (e.g. `require`) for the external URL only. `load_dotenv()` loads `.env`; `.env.example` documents both environments. Dev keeps SQLite both locally (`.env` absolute `DB_URL`) and in Docker (compose `DB_URL=sqlite:////app/data/expense_app.db`); `docker-compose*.yaml` is unchanged.

## SQLite notes

- No migrations — `Base.metadata.create_all(bind=engine)` runs at import time in `backend/main.py`. Edit models, restart to apply. Column additions (e.g. `Account.bank`) do NOT migrate an existing DB file — delete `expense_app.db` to regenerate the schema. (Alembic is in requirements but unused.) The `budget_limits` table (`account_id` column now NOT NULL) and the `categories.is_budget_source` column require the same regeneration: delete `expense_app.db` once and let the app/entrypoint recreate + reseed it.
- Two repo-root SQLite files exist, both gitignored (`*.db`): the dev DB `expense_app.db` (written by the container via the repo-root bind mount and by local runs via the absolute `DB_URL` in `.env`; delete it to regenerate the schema) and the test DB `expense_app_test.db`, which `tests/conftest.py` **deletes at the start of every pytest session** so `create_all` always builds a fresh schema (never delete it by hand).
- Tables are auto-created, but **categories are not seeded** on local runs. The Docker entrypoint seeds categories automatically via `backend/scripts/entrypoint.py` using `DEFAULT_CATEGORIES` — name + type + description + `is_budget_source` (only "Sueldo" is `True`) — and tests seed them lazily via the `category` fixtures; there is no manual SQL seed (the old `queries.sql` was removed as unused). Note the seed only runs when the `categories` table is empty, so existing DBs regenerated with the new column need the delete + reseed too. Creating an operation with a `category_id` that isn't active in the DB returns 400.

## Auth

- All authentication logic lives in the `backend/src/auth/` package: `Security` class (`security.py`), `LoadUserData` middleware (`middleware.py`), and `get_current_user` dependency (`dependencies.py`).
- The `backend/src/auth/__init__.py` uses lazy imports (no eager re-exports) to avoid triggering DB config loading at import time. Consumers must import directly from submodules: `from .security import Security`, `from .middleware import LoadUserData`, `from .dependencies import get_current_user`.
- JWT handled by `LoadUserData` middleware, not FastAPI dependencies. It decodes the `Authorization: Bearer <token>` header and sets `request.state.user` to a **dict** (`user.to_dict()`), so route/service code uses `user['id']`, not `user.id`. User accounts are eagerly loaded via `joinedload(User.accounts)` to prevent lazy-loading surprises. `User_Service.login` likewise eager-loads accounts and returns `(token, user.to_dict())`, so `POST /users/login` responde body `{access_token, token_type, user}` — the login body is the frontend's only source for the current user (it never calls a user-listing endpoint).
- **Middleware ordering**: in `backend/main.py`, `LoadUserData` is registered **before** `CORSMiddleware` so that CORS ends up the outermost middleware and answers `OPTIONS` preflights without hitting auth logic; `LoadUserData` also short-circuits `OPTIONS` requests (pass-through) defensively. `CORS_ORIGINS` dedupes `FRONTEND_URL` + `http://localhost:3000` + `http://frontend:3000` — the browser-facing origin (`localhost:3000`) differs from the compose-internal hostname (`frontend:3000`), so trusting only `FRONTEND_URL` breaks CORS in Docker. Every origin is normalized with `rstrip("/")` (`_normalize_origin`): Starlette matches `allow_origins` by exact string equality (`starlette/middleware/cors.py`) and the browser never sends a trailing slash in `Origin`, so a stray `/` would silently disable CORS. In production the Netlify origin is supplied via `FRONTEND_URL` (e.g. `https://operations-app.netlify.app`, no hardcoded origin in code).
- Tokens use PyJWT (`jwt`), payload is minimal: `sub` (user id) + `exp`/`iat`. `SECRET_KEY` (env `SECRET_KEY`, dev default), `ALGORITHM`, and `PasswordHash` live as module constants in `backend/src/auth/security.py` (single source of truth — do not hardcode elsewhere).
- Passwords are hashed with **argon2** via `pwdlib` (`PasswordHash.recommended()`). Rows hashed under the old passlib/bcrypt will not verify — re-register them.

## Style / structure

- Routes are registered imperatively: each route class's `__init__` calls `self.router.add_api_route(...)`; there are no decorators. New endpoints go in `backend/src/api/*_routes.py`, logic in `backend/src/services/*`. Current sets: `UserRoutes` (`/users` — only `POST /new` register and `POST /login`; the unauthenticated `GET /` user listing and `GET /{id}` profile were **removed** because they leaked every user's data), `AccountRoutes` (`/accounts` — `GET /` lists own active accounts, `POST /new` creates a zero-balance account), `CategoryRoutes` (`/categories` — read-only catalog of typed categories), `OperationRoutes` (`/operations` — CRUD/list, `POST /from-text`, y `GET /active-periods?account_id=` (meses con operaciones de la cuenta, newest-first; registrado **antes** de `/{id}` porque FastAPI resuelve por orden de registro)), `BudgetRoutes` (`/budgets` — monthly salary/budget summary and spending caps, see its own section below).
- Protected routes use `user: dict = Depends(get_current_user)` to enforce auth via the `LoadUserData` middleware; the dependency (`backend/src/auth/dependencies.py`) raises 401 when `request.state.user` is absent.
- Services return `JSONResponse` directly; the `response_model` on routes is effectively bypassed. The `to_dict()` on SQLAlchemy models is the de-facto serializer. `POST /users/new` returns `201` on success and `409` when the name/email is already taken (surfaced in the frontend `Register` form as an "ya registrado" warning). `POST /users/login` returns `404` for an unknown email and `400` for a wrong password — the frontend `Login` form surfaces them as distinct messages ("no existe un usuario registrado" vs "email o contraseña incorrectos"). `AuthProvider.login`/`register` rethrow after `SET_ERROR` so the pages only navigate on success.
- Currency whitelist lives in `backend/src/core/currencies.py`: `SUPPORTED_CURRENCIES` (env-overridable, default `USD,ARS`) plus `validate_supported_currency()`, shared by the `AccountCreate` and `CreateOperation` schemas (422 on rejection) — never re-implement the check in a service or model.
- Service class naming is inconsistent: `User_Service` (snake case) vs `OperationService`/`AccountService`/`CategoryService` — match the existing file's convention.
- Print-based debug statements are pervasive throughout; keep them when touching code (they're part of the current workflow).
- Balance model: `User` holds no balance — money lives in `Account.balance`. A new account is seeded on creation with a client-supplied starting `balance` (must be `> 0`) and a mandatory `bank` entity (non-null/non-empty); both are validated in `AccountCreate` (422 otherwise), the account is never zero-seeded. From then on the balance is **derived from operations**: `OperationService` applies a signed delta through the shared `_signed_delta(operation_type, amount)` helper (single source of truth: `income` → `+amount`, `expense`/`transfer` → `-amount`, both Spanish and English type strings are accepted, e.g. `transferencia`/`transfer`) and rejects any resulting balance at or below zero — the balance must stay **strictly greater** than zero after every mutation. `CreateOperation.amount` is validated in the schema (`Field(gt=0)`, 422 otherwise), so zero/negative amounts never reach the service (otherwise a negative debit would *grow* the balance). There is no manual balance endpoint. Updates (`PUT /operations/{id}`, `UpdateOperation` — all fields optional, `concept`/`amount` respect the same caps as creation) **revert the stored operation's balance effect first, then apply the new one** (so changing `type`/`amount` is always correct) and re-validate the category against the new type; deletes (`DELETE /operations/{id}`) reverse the stored effect and are rejected with 400 if the reversal would leave the balance ≤ 0.
- Operation date is always server-generated (`date` = utcnow at insert, plus `created_at` server_default) — clients never send dates. `OperationService.get_by_user` lists the user's operations ordered `date desc, id desc` (the frontend table re-sorts client-side per selected account, but the backend contract is deterministic). Free-text lengths match the `Operation` columns: `CreateOperation` caps `concept` and `name` at 250 chars (`Field(max_length=250)` → 422; keeps MySQL prod from a DataError 500), and the AI text pipeline truncates both `concept` and `name` to 250 in `to_operation_payload`.
- `Operation.name` (column in `backend/src/models/operation.py`; JSON key `name` everywhere — payload, response, DB) is an optional free-text column holding the merchant (purchase), service (payment/subscription), or person (transfer) associated with the operation — the specific meaning is inferred from `category`/`type` by the caller, not validated server-side. For `transfer` operations, `OperationService.create_new` defaults `name` to `"Other"` when the client omits it. The AI extraction prompt asks the model for `concept` as a brief but formal description of the operation based on the narration, including relevant details like the service and month, and for `name` with the official brand spelling (capitalization/accents, examples included); the backend stores `name` verbatim from the payload — there is no server-side brand dictionary.
- Operation currency: optional on `CreateOperation` (whitelist-validated like accounts, 422). When supplied it **must match the account's currency** (400 `Currency mismatch` in the service); when omitted the account's currency is snapshotted onto the operation.
- Gotcha: account ownership is centralized in `OperationService.get_owned_account(user_id, account_id, lock=False)` — 404 when missing, 403 when foreign; `lock=True` adds `with_for_update()` and must only be used right before mutating the balance, never across slow work (e.g. AI calls). `create_new` validates under lock; `TextOperationService.extract` pre-checks without it. `CreateOperation` carries only `account_id` + `category_id`, never a raw `user_id`.

- Every `Category` is tied to an `OperationType` via its `type` column (added on request, alongside the typed `DEFAULT_CATEGORIES` seed). Both `Category.type` and `Operation.type` use `SQLEnum(OperationType)`: on SQLite the column stores the enum **member name** (`expense`/`income`/`transfer`), while the API exposes the **value** (`Expense`/`Income`/`Transfer`) via `to_dict()` — so raw SQL against those columns must use the lowercase member names. `OperationService.create_new` rejects with 400 a category whose type doesn't match the operation type, `TextOperationService.to_operation_payload` matches the AI-suggested category by name AND normalized type against the active catalog, and the Dashboard filters `GET /categories/` options by the selected operation type.
- `Category.is_budget_source` (Boolean, default `False`, added for the budget module) marks the **income** categories whose operations count as the user's monthly "salary" budget. "Sueldo" is seeded flagged; bank capitalizations and other incomes ("Otros Ingresos") stay unflagged and appear in the summary as informational-only revenue that never grows the budget. The flag is not user-editable yet — it lives in the seed/DB only.

## Monthly salary/budget summary (`/budgets`)

- Authenticated endpoints registered by `BudgetRoutes` (`backend/src/api/budget_routes.py`):
  - `GET /budgets/summary?account_id=&year=&month=` (422 outside `1900..2100` / `1..12`): the analytical core — `BudgetService.monthly_summary` aggregates **the selected account's** operations (ownership enforced via the centralized `OperationService.get_owned_account` → 404/403) inside the **fiscal half-open month range** (`date >= [year,m,1) < next month`). **Everything is per-account on purpose**: each operation snapshots its account's currency, so the summary (and the caps compared against it) always lives in a single currency. Payload: `account_id/currency`, `year/month`, `total_salary` (sum of `income` ops whose `Category.is_budget_source` is true), `total_income` (all incomes, informational), `total_expenses` (sum of `expense` + `transfer` — both debit the budget), `net_available` (`total_salary - total_expenses`), `consumption_percentage` (`total_expenses / total_salary * 100`, **`null` when no salary income was registered** → the frontend shows the neutral/no-BMI state), `global_limit` (`{id, amount, used, percentage}` or `null`) and `categories` (debit ops grouped by category ordered by amount desc: `category_id/category_name/type/amount/count/percentage` — share of the total spend — plus `limit` with its progress when capped).
  - `GET /budgets/?account_id=&year=&month=`: every configured cap of the account/period (global first).
  - `POST /budgets/` (`BudgetLimitCreate` in `backend/src/schemas/budget.py`): **upsert** keyed by (user, account, year, month, category) — re-saving updates the `amount` and returns the same row (200), so the global cap stays unique without a unique index over the NULLable `category_id`. Payload `{account_id: int, category_id: null | int, amount (>0), month (1..12), year}`. The account must be owned (404/403 via the ownership helper). A category cap must reference an **active** category that is **not** an income one (income never consumes a budget → 400 "Income categories cannot have a spending limit"); unknown/inactive category → 400.
  - `DELETE /budgets/{id}`: 404 for nonexistent **and** foreign ids (mirrors the operation-delete scoping); 200 with `{"detail": "Budget limit deleted successfully"}` on success.
- Numeric guardrail: every sum coming from `Operation.amount` (`Numeric` → SQLAlchemy returns `Decimal`) is cast to `float` **at the query helpers** (`_sum_for_types`/`_sum_salary`) — mixing `Decimal` with `float` in the per-category percentage computation raises `TypeError`, and `json.dumps`-ing a `Decimal` inside a `JSONResponse` raises `TypeError: Object of type Decimal is not JSON serializable`.
- Period selection is data-driven: `OperationService.get_active_periods` (`OperationRoutes`, `GET /operations/active-periods?account_id=`, auth required) returns `{year, month}` pairs (newest first) of the fiscal months that contain at least one operation **of the selected account** (ownership 404/403 like the summary — a period is therefore always single-currency too), computed with dialect-portable `extract('year'/'month', Operation.date)` (never `strftime`/`to_char`/`DATE_FORMAT`). The report's `PeriodSelector` renders only those months (years = distinct period years; month options = active months of the selected year). When the current month has no operations on that account, `MonthlyReportView` falls back to the most recent active period; a failing periods fetch keeps the current-month selection as graceful default. Changing year keeps the month when still active for that year, otherwise jumps to the most recent active month of it.
- Model: `BudgetLimit` (`backend/src/models/budget_limit.py`) — `user_id` (FK users, `CASCADE`), `account_id` (**FK accounts, `CASCADE`, NOT NULL** — every cap is scoped to one account, matching the per-account summary), `category_id` (`FK categories`, NULLable → `NULL` = global cap), `amount` `Numeric(12,2)` (`CheckConstraint amount > 0`), `month`/`year`, timestamps, plus `UniqueConstraint(user_id, account_id, year, month, category_id)` (no-op for the global NULL row).
- Frontend (see below): page `app/(protected)/reports/monthly/page.tsx` + `src/features/reports/MonthlyReportView.tsx` (container: takes `accounts/selectedAccountId/selectAccount` from the `DataContext`, renders an `AccountSelectField` (id `report-account`) above the `PeriodSelector`, defaults to the current month, refetches on account/period/limit changes; no accounts → empty state "Aún no tenés cuentas" and it never calls the budget API) with `src/components/reports/` building blocks (`PeriodSelector`, `SummaryCards`, `GlobalLimitCard`, `CategoryBreakdown`, `BudgetProgressBar`) and `src/api/budgetApi.ts` (`getMonthlySummary`, `saveBudgetLimit`, `deleteBudgetLimit` — every call carries the `account_id`; the GET list endpoint has no frontend consumer: the summary already embeds the caps). The dashboard accesses it through the "Resumen mensual" button (`ROUTES.REPORTS_MONTHLY`). `SummaryCards` renders every amount with `formatCurrency(amount, summary.currency)` and, when `net_available < 0`, swaps the neutral subtitle for a red deficit warning (`data-testid="deficit-warning"`). Limit alerts use `consumptionLevel` in `src/utils/formatters.ts`: 🟢 < 75%, 🟡 75–99%, 🔴 ≥ 100%, `neutral` (gray) when no limit/percentage. The summary is the single fetch per render — limits are mutated with POST/DELETE and confirmed by refetching it. Backend `detail` extraction is shared in `src/utils/apiErrors.ts` (`backendDetail(err, fallback)`).

## AI text operations (`POST /operations/from-text`)

- JSON endpoint (no multipart): `text` (narración libre, 1..500 chars tras strip, 422 otherwise) + `account_id` (body), auth required. The `TextOperationCreate` schema lives in `backend/src/schemas/narration.py`; the response is `ExtractedOperationResponse` — **the extraction is never persisted**, the user confirms via the normal `POST /operations/new`.
- Pipeline (cheap-first): account exists/ownership (404/403, no row lock) → provider config (503) → AI call (502) → extraction validation/structuring (400) → currency match (400). `TextOperationService` (`backend/src/services/operation_text_service.py`) holds `build_extraction_prompt`, `parse_extraction`, `to_operation_payload`, `ensure_currency_matches` and `extract`; `provider_config` mirrors the old shared provider loader.
- Provider: any OpenAI-compatible `/chat/completions` endpoint, called through the official **`openai` Python client** (`OpenAI(api_key=API_KEY, base_url=API_URL)`; any `openai.OpenAIError` → 502). Env vars `API_URL`, `API_KEY` (add manually to `.env`; unset → 503), `AI_MODEL` (default `deepseek-v4-flash-free`, OpenCode Zen). Compose passes them through to the container.
- The prompt is written in **Spanish** (the app's target language); only the JSON field names and the `income/expense/transfer` enum values stay English because `AIExtraction` validates exactly those. It explicitly warns the model **not to translate** the JSON field names or the `income`/`expense`/`transfer`/`Other` literals (a key translated to Spanish surfaces as a 400 "required fields" via `AIExtraction`). It asks the model for strict JSON (`concept/amount/currency/type/name/category`) — defining `concept` as a brief but formal description of the operation based on the narration, including relevant details like the service and month, and `name` as the merchant/service/person written with the official brand spelling, with examples showing the split — injecting the account's currency code (`account_currency=account.currency`) so expressions like "pesos" map to ISO codes; `category` is matched by name AND normalized type against the active catalog (`category_options` passed in the prompt). The AI's free-form answer is normalized/validated once by `AIExtraction` (`backend/src/schemas/extraction.py`, single source of truth): `concept` non-empty, localized amounts (`2500`, `1.234,56`, `2,500` via `parse_localized_amount`), operation `type` through the shared `TYPE_ALIASES` in `backend/src/core/operation_types.py` — the same map `OperationService` uses, so a Spanish `egreso` from the model is accepted — and `currency` uppercased and whitelisted.
- Currency rules are strict at extraction time (per AGENTS decision): a suggested currency **outside** `SUPPORTED_CURRENCIES` is a **400** (never silently replaced by the account's currency); a **supported-but-different** one is a 400 (`Currency mismatch`, same message as `create_new`) via `TextOperationService.ensure_currency_matches` — so the preview never offers an operation that can't be created. Any other invalid extraction is a 400 with the offending field. `name` defaults to `None` (only `OperationService.create_new` turns transfer operations into `"Other"`), and `to_operation_payload` reverts a transfer's `otro`/`other` (a Spanish-model slip) back to `None` so that default still applies.
- The confirmed operation goes through the same rules as manual creation (balance delta, ownership, transfer → `"Other"`). No file-upload dep is required (`python-multipart`, `pypdf`, `pytesseract`, `Pillow`, `faster-whisper` were removed with the receipt/voice revert; `openai` stays).
- Frontend (`Dashboard.tsx` "Nueva operación" → tabs **Mensaje con IA** / **Formulario manual**, default manual): the AI tab posts the narration via `extractOperationFromText` (`frontend-next/src/api/operationsApi.ts`), renders the result as an editable preview (concept, amount, type, category filtered by type — changing the type resets the category to the first one of the new list; optional name), and confirms via the regular `createOperation` (`POST /operations/new`) sending **the selected account's `currency`** (the preview has no currency field, so a currency mismatch impossible; category/type mismatches are impossible too since the confirm button is gated on the category being in the filtered list). Backend `detail` is surfaced on extraction/confirm errors; a successful confirmation closes the form and returns to the operations panel, while "Nuevo relato" returns to the narration form.
- Tests: `tests/test_operation_text.py` is a pure unit suite over `TextOperationService` helpers with **no DB and no provider call**; `tests/test_narration.py` covers `/operations/from-text` paths that fail **before** the AI call (401/422/404/403). Following the suite-wide consolidation rule, each behaviour bucket is **one parametrized test**: prompt variants (currency rule with/without account), JSON parsing (valid/unparseable), valid payload mappings (full + Spanish aliases + transfer-name normalization), localized amounts, 400 rejects (validity fields, unmatched category), currency-match pass/400, and the two 422 text rejects. Frontend: `Dashboard.test.tsx` exercises the AI extract → preview → confirm flow plus the manual form.

## Tests

- `pytest` + `httpx` (used by `TestClient`) in `requirements.txt`. Run from the tests dir with `pytest` (the default flow), or from repo root with `python -m pytest tests -v`. Both work: `tests/conftest.py` puts the repo root and `backend/` on `sys.path` itself, so the tests' `src.*` imports (the same top-level modules the in-process app uses, e.g. `src.auth.security`, `src.core.operation_types`) resolve regardless of cwd.
- Tests run **in-process with no Docker**: `tests/conftest.py` deletes the repo-root test DB (`expense_app_test.db`) and forces `DB_URL` to it before importing the app, and the `client` fixture is a FastAPI `TestClient` over `backend.main.app`. The dev DB (`expense_app.db`) is never read or written by tests, so a test run never wipes development data.
- There is no reset endpoint, so per-test isolation comes from a direct `sqlite3` connection to the test DB: `truncate_tables` runs `DELETE FROM operations/budget_limits/accounts/users` before every test in FK order. `categories` are **not** truncated; the `category` fixtures reuse/insert active ones (and insert fallback rows on a fresh test DB).
- `test_auth.py` decodes JWTs with the dev-default `SECRET_KEY`/`ALGORITHM` from `src.auth.security` — importing that module is safe (no DB side effects); the app under test runs with the same default.
- Account setup in tests is centralized to avoid per-file duplication: `account_payload(**overrides)` (a fixture factory in `conftest.py`) builds the canonical `/accounts/new` JSON — defaults `name=Home, currency=USD, balance=400, bank=Test Bank` — and the shared `account` fixture creates one account via the API returning `{id, headers, category_id, category_income_id, category_salary_id, category_transfer_id}` (typed category ids supplied by the `category_factory(type_name, budget_source=False)` fixture, which reuses or lazily inserts an active category of that type — pass `budget_source=True` to require the `is_budget_source` flag for budget-summary tests). The `funded_account` fixture tiers on top of `account` by posting the canonical "Salary" 1000-`ingreso`, so every debit/balance test reuses it instead of repeating the funding POST (income-only and rejection tests stay on plain `account`, which never needs funding). Validation rejects are consolidated: **one parametrized test** in `test_accounts.py` (unsupported currency, zero/negative balance, null/empty/blank bank → 422), the strict-balance rule is **one parametrized test** in `test_operations.py` covering both `egreso` and `transfer` debits (equal to and over the balance → 400 "Insufficient balance"), non-positive `amount`s → 422 via the schema, and `concept`/`name` over 250 chars → 422 in **one parametrized test** (mirror of the backend `Field(max_length=250)` cap and the `to_operation_payload` truncation). Creation is split into `test_create_income_operation`/`test_create_expense_operation`; `GET /operations/` is covered for own-vs-foreign filtering and the newest-first ordering (`date desc, id desc`), and `GET /operations/{id}` for own (200), foreign and nonexistent (404). Register validation in `test_auth.py` is parametrized too. Second users for ownership/idempotency checks reuse `auth_headers(name=..., email=...)` instead of manually registering+logging in.
- `tests/test_operation_text.py` is a pure unit suite over the helpers of `TextOperationService` (validation, prompt, JSON parsing, payload mapping, currency mismatch) with **no DB and no provider call**, so it runs without a key (it imports the same `src.*` modules the in-process app uses, so it exercises a single module identity). The narration endpoint tests (`tests/test_narration.py`) cover the paths that fail **before** the AI call (401/422/404/403) plus **one full-flow happy path** (`test_from_text_extracts_and_confirms_full_flow`) with `call_provider` monkeypatched to a canned JSON — extract → preview payload → confirm via `POST /operations/new` → balance debited — still without any real provider call.
- `tests/test_budgets.py` covers the `/budgets` module (fully scoped to `account_id`: summary, caps and periods all take it and reject foreign accounts with 403 / unknown with 404 through the ownership helper) plus `GET /operations/active-periods?account_id=` (period constants computed from `utcnow` since clients can't send dates): one parametrized reject test (zero/negative `amount`, out-of-range `month`/`year` → 422; unknown category → 400), the income-category cap 400, a foreign-account POST 403, global-cap **upsert** idempotency (same id + one row), category cap with `category_name`, the summary totals/breakdown (salary-only budget vs plain income, expense+transfer consumption, per-category amount/count/percentage, `account_id`+`currency` echoed), limit progress in the summary (global `used/percentage` + per-category), own-account scoping (second user's spend never leaks), the **fiscal cutoff** (a previous-month operation inserted directly via `sqlite3` because the API always stamps `utcnow`), owner-scoped deletes (foreign/nonexistent → 404) and the active-periods endpoint (401 without auth; only months with operations on the selected account, newest first, foreign months excluded — also seeded via direct `sqlite3` inserts). Frontend: `src/__tests__/MonthlyReport.test.tsx` renders the view **inside the `DataProvider`** (mocks `@/api/budgetApi` + the full `@/api/operationsApi` — accounts/categories/operations plus `getActivePeriods`, fixture built from the runtime current month) and exercises KPI rendering, the no-accounts empty state, the account switch (`getMonthlySummary`/`getActivePeriods` are called with the newly selected id), the data-driven period selector (month/year no-ops for months without operations, same-year month switch, fallback to the most recent active period), global limit save/remove, category limit save, the surfaced backend `detail` and the deficit warning when `net_available < 0`.
- Tests are NOT run by the agent (Change rules) — the user executes `pytest` (from `tests/`) manually after every change.

## Frontend (Next.js — activo)

- **Framework**: **Next.js 15 (App Router)** + **React 19** + TypeScript, app en `frontend-next/` (la antigua SPA Vite `frontend/` fue eliminada).
- **Styling**: **Tailwind CSS** v3 (config en `frontend-next/tailwind.config.ts`; `globals.css` importado por `app/layout.tsx`). `postcss.config.mjs` declara los plugins **por nombre string** (`['tailwindcss', 'autoprefixer']`) — Next.js rechaza el estilo Vite de plugins-función ("Malformed PostCSS Configuration" al buildear).
- **Routing**: file-based (App Router) — `app/login/page.tsx`, `app/register/page.tsx`, y grupo protegido `app/(protected)/` (`layout.tsx` = `ProtectedRoute` + `DataProvider`; `page.tsx` = dashboard; `operations/new/page.tsx`; `operations/edit/page.tsx`; `accounts/new/page.tsx`; `reports/monthly/page.tsx` = resumen mensual de presupuestos). Interactivo con `'use client'`; `NewOperationForm` usa `useSearchParams` y se monta dentro de `<Suspense>` en su page. Las pages de `/operations/*` y `/accounts/*` son wrappers finos en `<Suspense>` que importan los componentes cliente desde `src/features/` (el App Router vive en `frontend-next/app/`, **no** en `src/app/` — crear ese directorio duplica el app dir y rompe el build). `/reports/monthly` no usa query params → wrapper directo sin `<Suspense>`.
- **Formularios como pages**: "Nueva operación" (`/operations/new`, tabs **Mensaje con IA / Formulario manual**, default manual) y "Nueva cuenta" ya **no viven en el dashboard** — son pages propias; el dashboard es solo lectura (selector + saldo + tabla, sin focus mode). El dashboard navega con `router.push` (`/operations/new?account=<id>` pasa la cuenta seleccionada al form).
- **HTTP**: Axios con interceptores (baseURL `NEXT_PUBLIC_API_URL || 'http://localhost:8000'`, JWT auto-injection; en 401 limpia el storage y dispara el evento `auth:unauthorized`, escuchado por `UnauthorizedRedirect` en `app/providers.tsx` → `router.push('/login')`).
- **Hosting**: `netlify.toml` + `@netlify/plugin-nextjs` (dep en devDependencies), build base `frontend-next/`. También tiene despliegue Docker: `frontend-next/Dockerfile` multi-stage (`deps` → `builder` → `runner`, `node:22-alpine`, usuario no-root) que requiere `output: 'standalone'` en `next.config.ts` y copia `public/` (placeholder `.gitkeep` incluido); `.dockerignore` excluye `node_modules/`, `.next/`, tests y configs locales. El build inlinha `NEXT_PUBLIC_API_URL`; sin la var, la app cae a `http://localhost:8000` (browser del host contra el puerto publicado de FastAPI).
- **Run (Docker)**: `cd frontend-next && docker build -t expense-frontend . && docker run -p 3000:3000 expense-frontend` (update: `npm run start` sigue funcionando local, pero el runtime recomendado en contenedor es `node server.js` via CMD del Dockerfile).
- **Forms**: React Hook Form + Zod (schemas en `features/auth/authSchema.ts` y `formSchemas.ts`). `Input.tsx` es `forwardRef`; todos campos con `autoComplete`.
- **State/auth**: Context + useReducer (`features/auth/AuthProvider.tsx` — `AuthContext` exportado; hooks: `hooks/useAuth.ts`).
- **Datos compartidos**: `features/data/DataProvider.tsx` es el dueño único de cuentas/categorías/operaciones y de `selectedAccountId` (un solo par `GET /categories` + `/operations` por montaje del layout protegido; predeterminadamente selecciona la primera cuenta). Los formularios reciben datos/mutaciones desde el contexto (`useData()`), equivalente a los viejos `useAccounts`/`useOperations`/`useCategories`; el reporte mensual (`MonthlyReportView`) también consume `accounts`/`selectedAccountId`/`selectAccount` para scoping por cuenta. `addAccount`/`addOperation` recargan ambas listas (saldo authoritative); `editOperation(id, data)` (PUT `/operations/{id}`) y `removeOperation(id)` (DELETE `/operations/{id}`) también recargan cuentas+operaciones tras cada mutación. "Nuevo relato" resetea en la misma page; confirmar/cancelar redirige al dashboard (`/`) con datos frescos.
- **Editar/eliminar operaciones**: `OperationsTable` tiene una columna **Acciones** (por fila) — "Editar" navega a `/operations/edit?id=<id>&account=<accountId>` (URL `OPERATIONS_BY_ID` sin slash final para evitar `/operations//<id>`) y "Eliminar" pide `window.confirm` antes de `removeOperation` (400 por reversión de saldo se pierde en el `alert` genérico). La page `/operations/edit` (`EditOperationForm` en `src/features/operations/`) carga la operación con `getOperationById` (GET `/operations/{id}`) y pre-llena `OperationForm` vía `initialData`; el mismo form cambia el botón a "Actualizar operación" y envía por `editOperation` (el prop `onAddOperation` es `Promise<unknown>` para CSP de tipos).
- **Componentes dashboard**: `AccountsPanel` (selector + balance integrado: recibe `selectedAccount` y embebe `SavingsBalance` dentro de su card), `SavingsBalance` (bloque sin card propio, solo consumido por `AccountsPanel`), `OperationsTable` (filtrado client-side, `date desc, id desc` del backend; columnas fecha/concepto/nombre/categoría/tipo/monto; chips de filtro rápido + layout apilado mobile, ver sus bullets arriba), `AccountSelectField`, `OperationForm` (manual, `typeRegister.onChange(e)` chaining obligatorio o RHF queda pegado al tipo default; `currency` nunca es campo del form — siempre la de la cuenta), `AIExtractionForm` (tabs + extracción editable + confirmación; hint textual bajo los tabs promocionando el modo IA y cita "Revisá los datos extraídos" marcando el paso de revisión de la preview) y `NewAccountForm` (name/currency/balance>0/bank). `-` cuando `name` es null. Dashboard header: botones "Nueva operación" / "Nueva cuenta" / **"Resumen mensual"** (`ROUTES.REPORTS_MONTHLY`) / "Cerrar sesión".
- **Responsive (mobile/desktop)**: la UI se adapta a pantallas angostas con jerarquía de acción principal — el header del dashboard apila título y botones (`flex-col gap-3 sm:flex-row sm:justify-between`) con "Nueva operación" como única acción `success size=md` y el resto en `sm` (Nueva cuenta `primary`, Resumen mensual `secondary`, Cerrar sesión `ghost`), `OperationsTable` habilita scroll horizontal dentro del card (`overflow-x-auto` en el wrapper, no `overflow-hidden`, que recortaba la tabla), y `GlobalLimitCard` permite wrapping en su header. Nueva clase Tailwind a replicar: siempre `overflow-x-auto` en tablas de ancho fijo y `flex-wrap`/stacking `sm:` en headers con varios botones — no reintroducir `overflow-hidden` en wrappers de tabla ni filas rígidas `justify-between` con botones múltiples.
- **Tablas responsive (`OperationsTable`)**: un solo DOM para desktop y mobile — debajo de `sm` cada `<tr>` es `flex flex-col` (card apilada, `gap-2` + celdas `py-2.5` para aire entre cards; el `divide-y` de `tbody` es el borde separador), el `thead` se oculta (`hidden sm:table-header-group`) y cada `<td>` muestra un `CellLabel` (`sm:hidden`) con el nombre de su columna antes del valor; desde `sm` todo vuelve a `table-row`/`table-cell` (nunca renderizar dos vistas paralelas duplicando el DOM: rompe los `getByText` únicos de las suites). **Barra de filtros** sobre la tabla (card, `border-b` inferior): **chips de tipo** (`TYPE_FILTERS`: Toda / Egresos / Ingresos / Transferencias, client-side, al elegir uno resetea la categoría) + **selector de categoría** (`#operations-category-filter`, catálogo-driven `categories.filter(is_active && matches type)` ordenado por nombre — **nunca derivado de las filas**: los textos de los `<option>` chocarían con los `getByText` de los tds; estilo pill, `ml-auto` en desktop); filtrado combinado tipo ∧ `category_id`; sin resultados → `<td colSpan={7}>` "No hay operaciones de este tipo y categoría"; al cambiar de cuenta el filtro de categoría vuelve a "Toda" (`useEffect` sobre `selectedAccountId`).
- **Barra de control unificada (reporte mensual)**: `MonthlyReportView` une `AccountSelectField` (ancho fijo `lg:w-72`) + `PeriodSelector` para cuenta y periodo en un único card (`bg-white shadow p-4`) — el selector de cuentas del Dashboard también integra el saldo: `AccountsPanel` recibe `selectedAccount` y renderiza `SavingsBalance` (**bloque sin card propio**, `mt-4 pt-4 border-t`) dentro de su card — el balance vive en el mismo bloque que el selector (en el Dashboard ya no se renderiza `SavingsBalance` aparte). El reporte pone así los KPIs más arriba del viewport; `SummaryCards`/`GlobalLimitCard`/`CategoryBreakdown` usan `p-4 sm:p-6` y montos `text-2xl sm:text-3xl`.
